# Reconcile graph behavior into a spec delta

Each capability has one behavior flow. Each outgoing edge of a Decision is one WHEN row, stored in `whens[edge.id]`, and may lead to an Action, another Decision, or an Outcome. Actions are path steps and may lead to Outcomes; they add no WHEN or THEN text. Outcome nodes store `then`. A case supplies the ordered Event-to-Outcome edge path and its target requirement/scenario name. The Markdown delta records the reviewed OpenSpec contract. Chart displays scenario links and Markdown read only; this skill owns their reconciliation.

1. Identify the change before change-specific inspection or editing. If the user has not explicitly named a change for this work, ask which change to use and wait for the answer. Do not infer it from the app's selection, the only active change, or the newest change directory; Chart's UI selection is not passed to this skill. Verify the named change exists and use that exact ID throughout. Do not create a change as a substitute for asking.
2. Run `openspec status --change <change-id> --json` and inspect the change's schema, artifact paths, dependency edges, and `applyRequires`. Reuse every existing artifact. If a required proposal is missing, inspect the selected graph and relevant project context, then create it before the spec delta from the user's intent and those findings. Follow `openspec instructions <artifact-id> --change <change-id> --json` for its path, template, and rules; do not hand-assume the default schema. Ask for a material missing reason or scope instead of inventing one. Never start a second change.
3. Inspect the capability's flow with `opsx-chart inspect --root <project> --capability <id> --change <change-id>` (provide `--flow <flow-id>` for a legacy project with several flows). Enumerate every complete Event-to-Outcome route, including routes without a case. Follow edges in order, passing through Actions without generating scenario lines. Collect the WHEN on each traversed Decision's outgoing edge, then the THEN on the final Outcome. A changed branch or Outcome may be shared by several routes: include every affected route. Stop and repair missing descriptors, disconnected paths, cycles, or conflicting shared text rather than inventing text from node or edge labels.
4. Match each route to an existing scenario in the active delta or current spec by its behavior. Reuse its requirement and scenario name when the match is clear; otherwise create a concise scenario under the appropriate requirement in the change. Surface a genuine ambiguity instead of silently choosing a conflicting scenario. Create or update one case per route in the flow draft, preserving stable IDs and references for unaffected cases. Remove stale case links whose route no longer exists. Never treat an intermediate Decision or Action as a separate scenario.
5. Run `opsx-chart scenario-template --root <project> --capability <id> --requirement <name> --scenario <name> --change <change-id>` for each target. Write the first Decision condition as `- **WHEN**`, every subsequent Decision condition as `- **AND**` in path order, and the final Outcome result as `- **THEN**`. Preserve the wording stored in node descriptors. A modified requirement delta must include the complete requirement text and all its scenarios; preserve unrelated requirements and scenarios already in the delta. Follow the schema's `specs` instructions when creating a missing delta; never create it when OpenSpec marks specs skipped.
6. Review the resulting Markdown against every affected case, then write the delta at the path resolved by OpenSpec for that capability. Keep canonical specs untouched until the normal sync phase. Refresh the OpenSpec snapshot, update every reconciled case's scenario reference to the change scope and new fingerprint, clear `pendingSpec`, and save the flow draft under the same change.
7. Re-run OpenSpec status. Complete every missing artifact in the transitive dependency set of `applyRequires`, in dependency order, using each artifact's `instructions --json` and existing dependencies as context. In the default spec-driven schema this normally means filling `design.md` and `tasks.md` after the proposal and spec delta. Inspect relevant code and tests so design choices and implementation tasks are grounded in the project; include graph work in the same task list. Preserve existing planning content, including artifacts already completed by `opsx-chart-propose`; do not overwrite it or mark implementation tasks done. Honor schema skips and conditional artifacts. If a plan cannot be derived from the graph and project context, ask for the missing decision rather than writing generic tasks.
8. Run `openspec validate <change> --strict --json` and `opsx-chart validate --root <project> --change <change>`. Resolve missing scenario links and incomplete node descriptors. Verify OpenSpec status has all apply-required artifacts and their dependencies satisfied. Report any case whose Markdown still differs from its graph WHEN/THEN and whether the change is ready for `opsx-chart-apply`.

This skill reconciles behavior and completes missing planning in the same change; it does not implement tasks, archive, or promote the change. Use `opsx-chart-apply` for implementation, then `opsx-chart-sync` after review.
